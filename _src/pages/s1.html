Session 1 WA3899 · Prompt Engineering for Analytics

Mind-reader not included

An AI model ships without a mind-reader. Whatever you leave out of a prompt (the timeframe, the definition, the consent rule, the real table names) it fills in with a confident guess. You never see the guess. You see a fluent answer. What you don't say, it makes up. Your job is to say it.

Words you will hear

LLM large language model
The engine behind Claude. It writes by predicting the next word-piece, over and over, from the text it can see.
Token
The word-pieces a model reads and writes. Roughly ¾ of an English word; lifecycle_events is several.
Context window
Everything the model can see right now: your prompt and the chat so far. It knows nothing else about HORIZON.
Temperature · sampling
How adventurous the next-token pick is. Above zero, the same prompt gives different answers.
Hallucination
A confident, fluent statement that isn't true, like a table name that doesn't exist.
Grounding
Giving the model the real facts it needs (tables, columns, rules) so it writes against reality instead of a guess.
Schema
The tables and their columns. In the database a schema is also a folder of tables: clr, mpl, ref.
Adoption
Here: distinct consumers who reached the trial or conversion stage. Without a definition, the model picks one for you.
Age-gate
A rule that blocks marketing to a group. In HORIZON nobody under 25 may be marketed to in Indonesia or Italy.
Consent
mpl.consent_records.marketing_allowed: whether we may market to that consumer at all.
Half-open date range
>= '2025-07-01' AND < '2025-10-01': the whole quarter, no "is the 30th included?" debate.
NULL
"Unknown". SQL has three truth values: true, false, unknown. WHERE keeps only true.
IS DISTINCT FROM
A comparison that treats NULL as a normal value, so unattributed rows are kept.
Few-shot
Showing the model one finished example so it copies your house style. Show, don't tell.
Chain-of-thought
Asking the model to list its plan (tables, joins, filters) before it writes SQL, so wrong assumptions surface early.
Template
A prompt with labelled {{PLACEHOLDERS}} that the next analyst fills in.
One minute

Before you start

Prompt hygiene, once

Everything you paste into an AI tool leaves your data boundary. Table names, column names and rules: yes. Real consumer rows, credentials, connection strings: never. HORIZON is fictional and nothing in this guide pastes a row, but build the habit here.

Ask it raw|Start the way most people do: just ask. What's our early VEEV adoption looking like in Indonesia? Respond in Markdown only — do not create a Word document or any file.

What you'll probably see: no query. Claude asks you questions: which timeframe? what counts as adoption? which data source? It may also say it can't see your data. That's the whole session on one screen: the model can tell the question is missing everything that matters.

If web search is switched on

Claude may instead summarise public news about PMI's VEEV launch in Indonesia. Notice what happened: it answered a different question (what the press says) because it couldn't see the one you meant (what HORIZON says). Same lesson, louder.

One word: what did it have to ask you for?

Now force it to guess, the way a busy analyst would. Same chat:

I don't have time for questions. Just write your best-guess SQL for our Postgres warehouse. The schemas are clr, mpl and ref. Use whatever tables and assumptions you think are reasonable. Respond in Markdown only — do not create a Word document or any file.

What this asks Claude to do: write a real query while knowing only three schema names. It has to invent everything else: table names, column names, the timeframe, the definition.

Will its query run against HORIZON?

Copy the SQL into your SQLTools tab and run it.

It errors on the first invented table, for example:

ERROR: relation "clr.consumer_lifecycle" does not exist

Look at how expert the query looks: common table expressions, a date spine, window functions, tidy aliases. It used the right schema names and still invented the tables, because it never saw them. Fluent is not grounded.

If your Claude happened to guess a real table and the query ran, read its WHERE clause: does it exclude under-25 consumers? Does it check consent? It had no way of knowing it should.

The real tables, for comparison:

SELECT table_schema, table_name FROM information_schema.tables WHERE table_schema IN ('clr', 'mpl', 'ref') ORDER BY 1, 2;
Hold on to this

An error is a gift. It tells you something is wrong.

The dangerous query is the one that runs and returns a believable number. Step 3 is that query.

Ground it|Give the model what it was missing, in a deliberate order: context first, the question last.

The silent zero|The Markets Lead adds one more ask: leave out the 2024 VEEV launch campaign.

Stay in the same chat and send:

Now also exclude the 2024 VEEV launch campaign (campaign_id 4) from the counts. Respond in Markdown only — do not create a Word document or any file.

Before you run anything, read the new WHERE clause. Most drafts add one line:

AND le.campaign_id <> 4 -- or: != 4 Campaign 4 has zero attributed events in HORIZON. So after excluding it, how many adopters should July show? And how many will this SQL return? Type two numbers.

Now run the typical draft in full: your Step 2 query plus that one line.

SELECT date_trunc('month', le.event_date)::date AS adoption_month, count(DISTINCT le.consumer_id) AS adopting_consumers FROM clr.lifecycle_events le JOIN clr.consumers c ON c.consumer_id = le.consumer_id AND c.market_code = le.market_code JOIN mpl.consent_records cr ON cr.consumer_id = le.consumer_id AND cr.market_code = le.market_code WHERE le.market_code = 'ID' AND le.product_code = 'VEEV' AND le.lifecycle_stage IN ('trial', 'conversion') AND le.event_date >= DATE '2025-07-01' AND le.event_date < DATE '2025-10-01' AND c.age_band <> '18-24' AND cr.marketing_allowed = true «AND le.campaign_id <> 4» GROUP BY 1 ORDER BY 1;

The right answer is "nothing changes": 17 · 16 · 25, because campaign 4 never had an event attributed to it.

Why: every single Indonesia event (2,343 of 2,343) has campaign_id = NULL, meaning "no campaign". And NULL <> 4 isn't true, it's unknown. WHERE keeps only true, so the "filter" throws every row away.

The lesson in one line

The structure you add to the prompt is what makes the answer trustworthy.

"Exclude campaign 4" sounded complete. It was missing the one rule (what to do with "no campaign") that decided the answer.

Placeholders in double braces: {{MARKET_CODE}}, {{PRODUCT_CODE}}, {{TIMEFRAME_START}}, {{TIMEFRAME_END}}, {{ADOPTION_STAGES}}, {{AGE_GATE_RULE}}, {{CAMPAIGN_RULE}}. 2. What this asks for, in plain English. Three prompting patterns in one template:

Pattern · the line that does itWhy it helps
Template · the {{PLACEHOLDERS}}Every placeholder is a hidden assumption from Step 1, now impossible to forget.
Chain-of-thought · "Before writing SQL, list the tables, joins and filters…"The model shows its plan first, so a wrong join or a missing NULL rule surfaces while it's cheap to fix.
Few-shot · the worked Indonesia exampleOne finished query locks in house style (comment header, join order, filter style) without re-spelling every rule.

What a good template looks like: labelled placeholders, the schema block, the rules block with {{AGE_GATE_RULE}} and {{CAMPAIGN_RULE}}, the "list your plan first" line, the worked example, and the question at the very end. If VEEV or 'ID' still appear outside the example, ask Claude to replace them.

Key takeaways

The model only knows what the prompt says.

Ground it in the real schema, define the metric, state the rules, and make it write its assumptions as comments. Everything you leave out, it fills in with a confident guess.

The warehouse is the arbiter.

An error is a gift; a query that silently returns the wrong population, or zero, is the danger. Run it and read the number. Then turn what worked into a template so the next prompt is reliable by default.
