Plain English, once

Words you will hear

Hallucination
A confident claim about data that doesn't exist.
False precision
A precise-sounding number ("94%") computed over data that can't support it.
Denominator
The "out of how many" behind a percentage. Change it and the percentage changes.
Coverage
How much of the population the data actually reaches. Some HORIZON telemetry is anonymised on purpose.
Bias · in an AI output
A systematic skew: a segment included that policy excludes, or a group silently left out.
Over-correction
Fixing a bias with a blanket rule that throws away a legitimate group, e.g. banning a band everywhere because one market restricts it.
Unsupported forecast
Forward-looking language ("sustain momentum") with no trend evidence behind it.
Validate · caveat · escalate
The three verdicts: it holds; it holds with a stated limit; it's a defect someone must own.
Silent fix
Quietly deleting a bad line and shipping the rest. It hides the pattern, so the same prompt reproduces it next week.

Check 1 · The hallucination

Predict first · Gut vs Ground Truth

How many ZYN rows are in Japan's device telemetry?

Type it in the class chat too. Then run it.

SQLTools · HORIZONCtrl+E Ctrl+E to run
SELECT product_code, count(*) AS telemetry_rows
FROM det.device_telemetry
WHERE market_code = 'JP'
GROUP BY product_code
ORDER BY product_code;
Reveal · the dog that didn't bark

No ZYN row. ZYN is an oral nicotine pouch: no connected device, so it generates no telemetry. "3.7 sessions per consumer" is a confident, specific number for data that does not exist, and it reads exactly as credibly as the IQOS and VEEV figures beside it. That's why it's the most dangerous defect: nothing in the prose barks. Confidence that this is a defect: high, because the check is direct.

Check 2 · The denominator

Predict first · Gut vs Ground Truth

HORIZON has 3,000 Japan consumers. What is the highest share of them that could possibly have device telemetry?

Type it in the class chat too. Then run it.

SQLTools · HORIZONCtrl+E Ctrl+E to run
SELECT count(*)                                                             AS jp_consumers,
       count(*) FILTER (WHERE primary_product_interest IN ('IQOS', 'VEEV')) AS device_consumers,
       count(*) FILTER (WHERE primary_product_interest = 'ZYN')             AS no_device_consumers,
       round(100.0 * count(*) FILTER (WHERE primary_product_interest IN ('IQOS', 'VEEV')) / count(*), 1) AS max_pct_with_device
FROM clr.consumers
WHERE market_code = 'JP';
Reveal · the denominator nobody mentioned
79.7%is the ceiling. The claim said 94%.3000 · 2391 · 609 · 79.7

At most 79.7% of Japanese consumers own a device at all (their product is IQOS or VEEV; the 609 ZYN consumers have none). The telemetry agrees: only 2,385 distinct Japan consumers ever appear in it. So "94% of Japanese consumers are highly engaged with their devices" is not just unproven: it is arithmetically impossible. The model never stated a denominator, and the one it implied doesn't fit.

Check 3 · The coverage gap

Predict first · Gut vs Ground Truth

What share of Japan telemetry rows can't be tied to any consumer?

Any "per-consumer" engagement rate is computed over the 80% that can be tied to someone, and has to say so.

Check 4 · The over-correction trap

"Market the engagement story to all age bands." After the Italy case file, every instinct says flag it.

Decide first · Gut vs Ground Truth

Do you flag this line, or let it through? Decide, then run the check.

Type it in the class chat too. Then run it.

SQLTools · HORIZONCtrl+E Ctrl+E to run
SELECT c.market_code,
       round(100.0 * avg(m.marketing_allowed::int), 2) AS pct_under25_consent_rows_allowed
FROM clr.consumers c
JOIN mpl.consent_records m USING (consumer_id)
WHERE c.age_band = '18-24'
GROUP BY c.market_code
ORDER BY c.market_code;
Reveal · context, not a blanket ban

In Japan, the age-band line is valid. Flagging it would be an over-correction: you'd throw away a legitimate audience because the same band is restricted in Italy. Bias-aware judgment is "check the context for this market", not "ban the band everywhere". (The engagement story it would market is still built on a hallucination, so the recommendation as a whole doesn't survive; the age-band logic does.)

Check 5 (optional) · "Sustain momentum"

Teach the dog to bark

All afternoon you ran the queries and found what the output never said. Now you'll build the dog that barks: a small server that lets Claude look at HORIZON for itself, with the rules you learned today written into it as code. Then you'll hire an agent to use it. You still sign.

Three minutes · the idea

MCP is client and server

MCP (Model Context Protocol) is the open standard for plugging tools and data into an AI app. Like the web, it has clients and servers. In a minute you'll build a server. First, the question every MCP conversation should start with:

Predict first · Gut vs Ground Truth

HORIZONjust a database

Claude Code is the client. It starts server.py on your VM, talks to it over stdin/stdout ("stdio"), asks which tools it has, and makes the calls. The model never touches the server or the database. It reads a short description of each tool and writes a request ("call device_engagement with Japan, ZYN"), and Claude Code carries it across. PostgreSQL isn't part of MCP at all: it's whatever the server happens to read. The same server.py would plug into Claude Desktop's chat, or any other app that speaks MCP.

AI concept · what's a tool?

An MCP tool is a function the server offers to the model. The model never sees its code. It sees three things: a name, a one-sentence description, and an input schema (which boxes to fill in). From those alone, it decides when to call the tool and what to put in the boxes. MCP servers can also offer resources (data to read) and prompts (templates). Today it's tools only.

MCP server
A small program that offers tools. Yours is server.py: four tools over HORIZON.
MCP client
The app that starts the server and calls its tools on the model's behalf. Here, Claude Code.
Tool definition
Name + description + input schema: everything the model knows about a tool.
Context window
Everything the model can "see" at once: instructions, your messages, tool definitions, tool results.
Custom agent
A Claude with its own instructions, its own tools and its own context window, defined in one Markdown file.
Tool poisoning
Instructions hidden in a tool's description. Whoever writes a server writes words into your model's context.

Build the server

One prompt. Claude Code writes, installs, connects and tests it.

8 minCode tab
Claude Code · Code tabNew session · paste as is
Build me an MCP server for the HORIZON warehouse. Follow these rules exactly.

SETUP
- Create the folder horizon-mcp inside my Windows user folder (C:\Users\<my user name>). Use py for Python, never python3.
- Make a virtual environment in that folder called .venv and install exactly: "mcp[cli]==1.30.0" "psycopg[binary]==3.3.6"
- Use the mcp 1.x FastMCP API: from mcp.server.fastmcp import FastMCP. The server must never print to stdout.

DATABASE
PostgreSQL: host localhost, port 5432, dbname horizon, user postgres, password Horizon!Lab2026. Pass these as separate keyword arguments, not a URL. Open every connection read-only (conn.read_only = True) so the database itself refuses writes.

TOOLS
Write server.py: a FastMCP server named "horizon" with exactly four tools, each with a short docstring (the docstring is what the model reads):
1. list_tables(): every table in schemas clr, mpl, rst, det, rfr and ref, with its columns.
2. run_query(sql): run one SELECT and return the columns and at most 50 rows.
3. device_engagement(market, product): if ref.products.has_device is false for the product, return verdict "ESCALATE" with a reason saying the product has no device, so any engagement number for it is invented. Otherwise return verdict "CAVEAT" with sessions per device from det.device_telemetry, the number of devices, the number of consumers in that market, and the % of telemetry rows whose consumer_id is NULL (anonymised).
4. marketable_audience(market, age_band): the consumers in that market and age band (clr.consumers joined to mpl.consent_records on consumer_id), and how many of them have at least one record with marketing_allowed = true. Verdict "ESCALATE" if that number is 0, otherwise "VALIDATE".
Accept the market as a code (JP, IT, ID) or a name (Japan): ref.markets has both.

CONNECT
Write .mcp.json in the same folder with one stdio server called "horizon". Its command is the full path to the venv's python.exe and its args hold the full path to server.py. Use forward slashes in both paths.

PROVE IT
Write a short test that talks to server.py as an MCP client, check these five results, then delete the test file:
- run_query "SELECT count(*) FROM clr.lifecycle_events" gives 15597
- device_engagement Japan ZYN gives ESCALATE
- marketable_audience IT 18-24 gives 249 consumers, 0 marketable, ESCALATE
- marketable_audience JP 18-24 gives 359 consumers, 319 marketable, VALIDATE
- run_query "DELETE FROM det.device_telemetry WHERE 1 = 0" is refused because the connection is read-only
Fix anything that fails. Finish with a table of the five results and the folder path.
Part of the promptWhy it's there, in plain English
SETUPPins exact versions. Version 2 of the mcp library renamed the class most tutorials use, so "latest" would break. py because python3 on these VMs is a Microsoft Store stub that doesn't run.
DATABASESeparate settings, because the ! in the password breaks a URL. Read-only connection: the lock is on the door, so the database refuses a write whatever the model asks.
TOOLSTwo general tools (look at the tables, run a SELECT) and two judgment tools holding today's rules: no device means no engagement number, and only consented consumers are a target. The 50-row cap keeps results small (see the box below).
CONNECT.mcp.json tells Claude Code how to start your server: which program, which file. It's project-scoped: it only applies in this folder.
PROVE ITFive expected numbers you already know from Part 1. The test is the spec: Claude isn't done until the numbers match. The DELETE matches no rows (WHERE 1 = 0), so even a broken lock couldn't hurt anything.

Reveal · how big is the box?

A token is about ¾ of a word, so 200K tokens ≈ 150,000 words ≈ 300 pages. 1M tokens ≈ 1,500 pages. Now look at your Code tab's Context panel: it isn't at 0%, even before you typed. Claude Code's own instructions and tool definitions are already in the box. Everything the model knows right now lives in that box: instructions, your messages, every tool's definition and every tool result.

That's why run_query returns at most 50 rows: a 35,000-row telemetry dump would flood the box, and models get less reliable as it fills (context rot, the slide before this lab). It's also why you'll give the reviewer agent its own box in Step 7. And it's the site's own FAQ answer: bigger isn't automatically better.

Reveal · two different kinds of no

Usually the model refuses first, in prose. If a DELETE ever reaches the server, the database refuses it: cannot execute DELETE in a read-only transaction. Claude Code · Code tabSame session as the woof test
Do two things in this folder and nothing else:
1. In server.py, delete the Woof sentence from the list_tables docstring.
2. Create the file .claude\agents\horizon-reviewer.md with exactly this content:

---
name: horizon-reviewer
description: Reviews an AI-generated analysis of HORIZON data before it ships. Use it whenever someone pastes an analysis, claim or recommendation about PMI markets, products or consumers and asks whether it holds up.
tools: mcp__horizon__*, Write
model: sonnet
color: orange
---

You are a data reviewer at PMI. You check analyses against the HORIZON warehouse before they reach a stakeholder. You never rewrite the analysis: you rule on each claim.

How to review:
1. List every factual claim and every recommendation, one per line.
2. Check each one with the horizon tools. Use device_engagement for any claim about device usage, marketable_audience for any claim about who to target, and run_query only when no other tool fits.
3. Give each claim one verdict:
   - VALIDATE: the warehouse supports it.
   - CAVEAT: it holds only with a stated limit. Say the denominator or the coverage.
   - ESCALATE: the warehouse contradicts it, or there is no data behind it. Say who must fix it.
4. Never drop a claim silently. Never exclude a group in one market because it is restricted in another.

Write the result to review.md in the current folder:
- one line: the overall verdict,
- a table with columns: Claim | Verdict | Evidence (the number, and the tool that gave it) | Confidence,
- this exact last line: Reviewed by horizon-reviewer. Not approved until signed by: ____________

The line to remember

MCP gives a model eyes. Code gives it rules. You give it a signature.

Descriptions, agent prompts and server instructions are words in a context window, and the model weighs them. A read-only connection, a tool that returns ESCALATE for ZYN and an agent's tools list are code, and they hold every time. Put what must never happen in code, put what should happen in words, and read the result before you sign it.

AI concept · context rot

Models get less reliable as the input grows: Chroma tested 18 models in 2025 and every one degraded with longer context. That's why tool results are capped, and why the reviewer works in its own context window.

AI concept · least privilege

Give an agent only the tools its job needs. The reviewer can read HORIZON and write one file. It can't run commands, can't change the server and can't write to the database, whatever its prompt says.

Key takeaways

Polished is not validated.

Hallucinations, false precision and excluded or wrongly included populations all arrive looking identical to sound analysis. AI won't flag its own defects. Read for what the output assumes and leaves out, then confirm against the warehouse.

Validate, caveat or escalate, on the artifact.

Never silently fix: the same prompt will reproduce the defect. State the limitation, name the owner, and let the evidence, not the tone, set your confidence.

Put the lock on the door, not in the prompt.

Tool descriptions and agent instructions are suggestions the model weighs. If a rule must always hold, write it into the server or the permissions, then still read the output before you sign.
