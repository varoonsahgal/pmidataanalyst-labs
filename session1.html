Session 1 WA3899 · Prompt Engineering for Analytics

Mind-reader not included

An AI model ships without a mind-reader. Whatever you leave out of a prompt (the timeframe, the definition, the consent rule, the real table names) it fills in with a confident guess. You never see the guess. You see a fluent answer. What you don't say, it makes up. Your job is to say it.

Theme · Session 1 of 4 Today's theme

Mind-reader not included

Every silence in your prompt gets filled. Leave out the timeframe and it picks one. Leave out the definition of "adoption" and it invents one. Leave out the consent rule and it counts people the business may not market to. None of it shows up as a warning.

What you don't say, it makes up.

Words you will hear

LLM large language model
The engine behind Claude. It writes by predicting the next word-piece, over and over, from the text it can see.
Token
The word-pieces a model reads and writes. Roughly ¾ of an English word; lifecycle_events is several.
Context window
Everything the model can see right now: your prompt and the chat so far. It knows nothing else about HORIZON.
Temperature · sampling
How adventurous the next-token pick is. Above zero, the same prompt gives different answers.
Hallucination
A confident, fluent statement that isn't true, like a table name that doesn't exist.
Grounding
Giving the model the real facts it needs (tables, columns, rules) so it writes against reality instead of a guess.
Schema
The tables and their columns. In the database a schema is also a folder of tables: clr, mpl, ref.
Adoption
Here: distinct consumers who reached the trial or conversion stage. Without a definition, the model picks one for you.
Age-gate
A rule that blocks marketing to a group. In HORIZON nobody under 25 may be marketed to in Indonesia or Italy.
Consent
mpl.consent_records.marketing_allowed: whether we may market to that consumer at all.
Half-open date range
>= '2025-07-01' AND < '2025-10-01': the whole quarter, no "is the 30th included?" debate.
NULL
"Unknown". SQL has three truth values: true, false, unknown. WHERE keeps only true.
IS DISTINCT FROM
A comparison that treats NULL as a normal value, so unattributed rows are kept.
Few-shot
Showing the model one finished example so it copies your house style. Show, don't tell.
Chain-of-thought
Asking the model to list its plan (tables, joins, filters) before it writes SQL, so wrong assumptions surface early.
Template
A prompt with labelled {{PLACEHOLDERS}} that the next analyst fills in.
One minute

Before you start

Prompt hygiene, once

Everything you paste into an AI tool leaves your data boundary. Table names, column names and rules: yes. Real consumer rows, credentials, connection strings: never. HORIZON is fictional and nothing in this guide pastes a row, but build the habit here.

What usually happens

It errors on the first invented table, for example:

SQLTools · error
ERROR:  relation "clr.consumer_lifecycle" does not exist

Look at how expert the query looks: common table expressions, a date spine, window functions, tidy aliases. It used the right schema names and still invented the tables, because it never saw them. Fluent is not grounded.

If your Claude happened to guess a real table and the query ran, read its WHERE clause: does it exclude under-25 consumers? Does it check consent? It had no way of knowing it should.

The real tables, for comparison:

SQLTools · HORIZONCtrl+E Ctrl+E to run
SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_schema IN ('clr', 'mpl', 'ref')
ORDER BY 1, 2;
Hold on to this

An error is a gift. It tells you something is wrong.

The dangerous query is the one that runs and returns a believable number. Step 3 is that query.

SQLTools · HORIZONWhat the age-gate removed, month by month
-- What the age-gate removed, month by month
SELECT date_trunc('month', le.event_date)::date AS adoption_month,
       count(DISTINCT le.consumer_id)                                      AS all_adopters,
       count(DISTINCT le.consumer_id) FILTER (WHERE c.age_band <> '18-24') AS after_age_gate
FROM clr.lifecycle_events le
JOIN clr.consumers c USING (consumer_id)
WHERE le.market_code = 'ID'
  AND le.product_code = 'VEEV'
  AND le.lifecycle_stage IN ('trial', 'conversion')
  AND le.event_date >= DATE '2025-07-01'
  AND le.event_date <  DATE '2025-10-01'
GROUP BY 1
ORDER BY 1;

Reveal: the silent zero
0 rowsNo error. No warning.A dashboard built on this would say nobody adopted VEEV in Indonesia.

The right answer is "nothing changes": 17 · 16 · 25, because campaign 4 never had an event attributed to it.

Why: every single Indonesia event (2,343 of 2,343) has campaign_id = NULL, meaning "no campaign". And NULL <> 4 isn't true, it's unknown. WHERE keeps only true, so the "filter" throws every row away.

The lesson in one line

The structure you add to the prompt is what makes the answer trustworthy.

"Exclude campaign 4" sounded complete. It was missing the one rule (what to do with "no campaign") that decided the answer.

Two of those patterns, up close: few-shot and chain-of-thought

You'll meet these two far beyond today's template, so each gets a two-minute example you can paste. Run them if you're ahead; if not, read the typical answer and move on.

Pattern 1 · Few-shot

Show it, don't describe it

Give the model two or three finished examples of exactly what you want, then the new case. It copies the shape of the examples: the format, the level of detail, and the habits inside them.

Two examples here teach two things at once: the four-field format, and the house habit of writing ASSUMPTION where the request is silent. Then comes the question this whole lab started with.

Claude Desktop · SonnetOptional · 1 min · a new chat works best
Turn each request into four fields: MARKET, PRODUCT, TIMEFRAME, METRIC. Where the request does not say, write ASSUMPTION and what you would need to ask. Follow the examples exactly.

A typical answer · yours will differ in wording
MARKET: ASSUMPTION · no market is named. Which market is this about?

Without the examples

Describe the format in words and you get a different shape each time, with the blanks quietly filled in. That is Step 1: "early VEEV adoption" came back with invented tables, plus a timeframe and a definition it never told you it had picked.

With two examples

The same four lines every time, and three of them say ASSUMPTION. The model named the gaps instead of filling them, because the examples showed it that's what we do here.

In your template: requirement 5, the worked Indonesia query, is few-shot with a single example (people say "one-shot"). It teaches house style, the comment header, the join order and the NULL-safe filter, without re-spelling every rule.

Pattern 2 · Chain-of-thought

Make it think on the page

Ask for the reasoning before the answer: the cases, the steps, the plan. It doesn't make the model smarter. It puts the guess where you can read it, so you check the plan before you run the SQL. Newer models do some of this silently; asking for it in writing puts it in front of you.

Here is Step 3's trap again, this time with the reasoning requested up front. Watch where the word unknown appears.

Claude Desktop · SonnetOptional · 1 min · new chat
Context: in clr.lifecycle_events, campaign_id is an integer column. It is NULL on every event that was not attributed to a campaign.
Task: add a filter so that events attributed to campaign 4 are excluded, and nothing else is.

Before writing any SQL, reason in numbered steps:
1. Which values can campaign_id hold on a row?
2. For each of those values, what does campaign_id <> 4 evaluate to: true, false or unknown?
3. Which of those rows does WHERE keep?
Then write the one-line filter you recommend, and say why.

Respond in Markdown only — do not create a Word document or any file.
A typical answer
1. campaign_id is 4, some other number, or NULL (unattributed).
2. 4 → false. Another number → true. NULL → unknown: any comparison with NULL is unknown.
3. WHERE keeps only true. Campaign 4 rows go (good), other campaigns stay (good), and every NULL row is dropped too (bad: those are the unattributed events we want to keep).

Recommended:  AND campaign_id IS DISTINCT FROM 4   -- removes campaign 4 only; keeps NULL
Without the steps

You get AND campaign_id <> 4, fluent and wrong, and the first sign of trouble is zero rows on a dashboard.

With the steps

Step 2 says unknown and step 3 says dropped, before any SQL exists. Even if the model had still recommended <> 4, you'd have caught it reading the plan.

In your template: requirement 4, "Before writing SQL, list the tables, joins and filters you will use, and how you will treat NULL values", is this pattern generalised to every future question. The plan is what you review. The SQL is what you run. The warehouse still decides.

Key takeaways

The model only knows what the prompt says.

Ground it in the real schema, define the metric, state the rules, and make it write its assumptions as comments. Everything you leave out, it fills in with a confident guess.

The warehouse is the arbiter.

An error is a gift; a query that silently returns the wrong population, or zero, is the danger. Run it and read the number. Then turn what worked into a template so the next prompt is reliable by default.
